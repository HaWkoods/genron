# 数学原論　制作方法論

制定：2026-11-26（初期版）。

## 基本方針
ブルバキの構造的な思想を参照し、独立したノートではなく一つの数学体系として制作する。分野横断的な共通構成（部分・商・積・自由構成・普遍性等）を重視する。原論の全体構造は全順序ではなく、基礎から発展へ向かう有向非巡回グラフ（DAG）とする。分岐・合流を認め、知識の依存関係、ノート番号、制作順序を区別する。異なる枝の先行知識を不必要に要求しない。暫定案は確定規約と混同しない。数学的言語としての論理・集合と研究対象としての論理・集合を区別する。数理論理学・現代的集合論は後続の発展的・応用的な枝に置き、初期の前提科目としない（docs/foundations.md）。

## 品質優先の原則

ユーザーの明示的な要請（2026-11-26）により、制作速度より数学的厳密性・体系全体との整合性・記述と組版の品質を優先する。短時間で提出すること自体を目標とせず、利用可能な作業時間・計算資源の範囲内で必要な調査、再検討、修正と検証を行う。

- 文献調査・構成設計・執筆・数学的査読・台帳検証・組版確認を省略しない。論証の難所では複数の証明方法や定義を比較し、循環、暗黙の仮定、例外、退化例を吟味する。
- 初稿を直ちに完成稿とみなさず、数学的正確性と全体の依存関係、文章・記法、コンパイル結果を別の観点から点検し、必要な修正後に再検証する。
- 一度の実行で全工程を完了できない場合には、検証可能な区切りで原稿・台帳・進捗・残存課題を保存する。完了した工程と未実施の工程を明示し、未検証部分を完成品と称さない。実行制約を理由に厳密性の水準を下げない。
- 時間を費やすこと自体を目的とせず、追加の検討が品質向上に資する範囲で作業する。作業が完了したと報告する前に成果物と検証結果を確認する。

## 制作の手順
1. AGENTS.md、本書、docs/knowledge.md、docs/knowledge.json、docs/references.md、docs/foundations.md、関連原稿の最新版を読む。
2. 対象ノートの位置と、対象知識の直接前提・その推移閉包を確定する。無関係な先行ノートは前提としない。実質的な集合存在原理・追加公理は明示し台帳に登録する。前提が未確定なら明示して草稿扱いとする。
3. Google Drive の所蔵数学文献を積極的に調査し、必要なら公開文献を補足する（docs/references.md）。実際の参照箇所、仮定、定義、証明方法を比較した上で構成案を立て、導入する定義、公理、結果、構成と直接依存先を台帳に登録する。
4. 数学書調の厳密な原稿を執筆する。既出の結果は恒久IDと表示上の所在を用いて参照し、循環・先取り・暗黙の仮定を避ける。原稿を genron:begin/end で囲み、genron:use で直接依存を注釈する。
5. 各証明の論理、定義の適法性、仮定、記法の整合、依存関係、到達点を点検する。知識およびノートの両階層の依存グラフの循環、参照切れ、未確立事項の使用を検査する。`graph notes`、`graph knowledge`、`prerequisites ID` で構成を確認する。`node scripts/test-knowledge.mjs` と `node scripts/knowledge.mjs check` を実行し、正式版では `check --strict` を用いる。これらは無矛盾性の形式的証明を意味しない。
6. pLaTeX原稿では原則 platex 2回、dvipdfmx、ログ調査、全ページの目視確認を行う。実行不能ならpLaTeX原稿を保持し、未検証事項を報告する。XeLaTeXへの恒久置換は禁止。
7. 原稿と台帳の状態・到達点・依存関係を同期してコミットする。可能なら一つの変更単位にまとめ、複数コミットの場合は途中状態を草稿と扱う。
8. 作業中の添削・指摘から一般化できる規約を本書または対応する規約文書へ追記する。変更の理由と影響範囲を記す。数学的知識は必ず台帳を正本とする。
9. ユーザーに変更ファイル、コミット、検証結果、未実施事項、暫定判断を報告する。

## 組版・文体の暫定方針
従来の共通pLaTeXテンプレート第2版を参考に、A5判・本文10pt・装飾を抑えた硬質な数学書調を採用する方向とする。テンプレート実体や最終的な書式は未整備であり、確定時に記録する。厳密性をページ数より優先する。

## 改訂
原稿の修正に際して、`node scripts/knowledge.mjs impact ID...` または `impact --base COMMIT` で逆依存を調査し、影響を受ける結果・到達点を再検証する。変更の影響が不明な場合は要再検証とする。承認済みの規約の変更、基礎体系の変更など大きな決定は、暫定案と区別しユーザーの確認を得る。

台帳の正本は docs/knowledge.json とする。docs/knowledge.md は形式と運用規則のみを記述し、知識の二重管理をしない。

文献調査では Google Drive の資料を優先的に活用する。文献の記述順や前提を無条件には採用せず、知識台帳と整合する論証に再構成する。参照文献と確認範囲を記録する。

## PDF掲載

検証済みノートのPDFは `volumes/N-番号/main.pdf` としてGitHubに掲載する。`node scripts/publish-pdf.mjs N-番号` は厳格な台帳検証・pLaTeX二回・dvipdfmx・pdfinfoを実行し、成功後にPDFと総目次を生成する。main の関連変更では GitHub Actions の Publish verified note PDFs が同じ処理を行い、PDFと目次をコミットする。原稿が verified でPDFが存在するノートのみ、総目次の題名に相対リンクを生成する。掲載の成功とPDFの内容・目視確認は別に検証する。

## 復習・確認用の一覧

定義・命題一覧 `docs/statements.md` を知識台帳から生成する。読者が定義や命題の仮定と結論を確認するためのもので、証明・解説は掲載しない。`node scripts/knowledge.mjs statements > docs/statements.md` で台帳と同期し、PDF掲載処理とCIにも組み込む。

定義・命題一覧はPDFを正規の閲覧形式とし、A5判・本文10ptの暫定共通書式を継承する。`scripts/statements-tex.mjs` で台帳から原稿を生成し、pLaTeX 2回、dvipdfmx、ログ検査、全頁確認を実施する。`scripts/publish-pdf.mjs` に原稿・PDF・Markdownの同期を統合した。生成後のPDFを確認し、総目次及びREADMEから直接閲覧できるようにする。

## 電子閲覧サイト

[検索・PDF閲覧サイトの設計](viewer-design.md) に従い、恒久IDに基づく参照移動・知識項目のプレビューを整備する。プレビューの初期幅は580px、上下左右の余白は28pxとし、読者が調整できるようにする。現段階では設計記録であり実装完了を意味しない。
